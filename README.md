# skills

Agent skills for reviewing code through [crit](https://github.com/tomasz-tomczyk/crit), plus the
Linear and attribution helpers they lean on.

The review pair splits on **whose code it is**, which is the thing that decides what the agent is
allowed to do:

| | |
|---|---|
| **`/review-pr`** | Someone else's PR. Authors findings as crit inline comments, iterates with you in the browser, and posts to GitHub only when you say so. **Never edits code.** |
| **`/revise`** | Your own code. Reviews local changes before anyone sees them, or takes the reviewers' threads on your open PRs and closes them out. The only one that edits. |
| `review-exchange` | The contract both sides share — the badges a finding carries, the verdict badges an answer carries, the confidence ladder, the cite rules, who resolves. One edit there reaches both. |

Findings live in a `findings.json`, and `review-pr/scripts/render.py` is the only thing that turns a
record into text — crit body, GitHub comment, ledger row, review body. Hand-written copies of a finding
are how a ledger ends up disagreeing with its own threads.

```
skills/
  review-pr/         SKILL.md · references/ · scripts/
  revise/            SKILL.md · FLEET.md
  review-exchange/   SKILL.md · config.example.md
                     references/ — crit-mechanics · github-review-api · crit-review-outline
  ai-ethics/         attribution marker for anything published
  linear-comment/    comments on Linear issues and projects
  linear-ticket/     small, scannable Linear tickets
```

## 1. What you need installed

**`crit`** is the one thing that isn't standard. It is a local binary that renders a diff in your
browser with an inline-comment UI, and it is how you and the agent talk during a review. Verified
against **crit 0.18.4**.

```bash
brew install crit
# or: go install github.com/tomasz-tomczyk/crit/cmd/crit@latest
# or: nix profile install github:tomasz-tomczyk/crit
# or grab a release: https://github.com/tomasz-tomczyk/crit/releases/latest
```

You need the **binary on your PATH — not** crit's own agent plugin. These skills drive crit through
their own scripts (`review-pr/scripts/crit.sh`), so crit's `/crit` slash command is a separate thing
you can install or skip.

Also required, all of which you probably have:

| | |
|---|---|
| `gh` | authenticated (`gh auth login`) — every PR fetch, comment and review goes through it |
| `jq` | the scripts parse GitHub JSON with it |
| `python3` | runs `render.py` and `prune_authored.py`; no third-party packages |
| `git` | worktrees, specifically — `/review-pr` reviews the PR in a throwaway worktree rather than checking it out over your branch |

Check it in one line:

```bash
for c in crit gh jq python3 git; do command -v $c >/dev/null || echo "missing: $c"; done
gh auth status
```

## 2. Install the skills

**Claude Code** — one command, because `.claude-plugin/` is in this repo:

```
/plugin marketplace add ylkhayat/skills
/plugin install review-skills@ylkhayat-skills
```

**Any other agent that reads `SKILL.md` folders** — clone once, then symlink the skill directories
into wherever your agent looks:

```bash
git clone https://github.com/ylkhayat/skills.git ~/src/review-skills
ln -s ~/src/review-skills/skills/* <your agent's skills dir>/
```

| Agent | Skills directory |
|---|---|
| OpenClaw | `~/.openclaw/skills/` |
| Claude Code (manual) | `~/.claude/skills/` |
| OpenCode | `~/.config/opencode/skills/` — it also scans `~/.claude/skills/` |
| Codex | `~/.codex/skills/` |
| Neutral / several at once | `~/.agents/skills/`, then symlink that into each agent's dir |

Symlinking beats copying: `git pull` updates every agent at once.

**Take all of them, or take `review-pr` + `revise` + `review-exchange`.** The two review skills read
shared files out of `review-exchange` as `../review-exchange/…`, so it has to sit beside them. The
Linear and ai-ethics skills are independent — take them or leave them.

## 3. Configure

```bash
cp skills/review-exchange/config.example.md skills/review-exchange/config.md
```

One table, and it is the only file you edit. The skills are orchestration and read their values from
it, so nothing in `skills/` hardcodes anything that belongs to a particular repo or team:

| Row | What it changes |
|---|---|
| `repos` | which repos `/revise` searches for PRs with feedback waiting on you |
| `trunk branches` | how `/review-pr` notices a PR is stacked on another PR rather than on trunk |
| `install` / `typecheck` / `lint` | run in the background during Phase 0; a red typecheck becomes a finding with its repro already attached |
| `fix` | run before `git add` so formatting never lands in a follow-up commit |
| `test` | the shape of the repro line in a finding |
| `convention files` | globs for your house rules; gathered once, cached, and passed to agents as a path |
| `review bots` | which comment authors get triaged as bots rather than humans |
| `playbook skills` | per-area skills the fan-out tells each agent to load |
| `issue tracker` | your ticket key format and state names, for the ticket gate |
| `my login` | whose name goes on a `flagged`/`endorsed` badge |

A wrong or blank row degrades rather than breaks: the tooling rows are guarded by *skip when the repo
has no such script*, and an empty playbook or bot row is one less input to the review. `config.md` is
gitignored, so your values stay yours and `config.example.md` is what ships.

## 4. Run it

```
/review-pr 3266        # or just /review-pr on the PR's branch
/revise                # pick from your PRs with feedback waiting
/revise main           # review local changes against trunk first
```

`/review-pr` hands you a crit URL in its first message and keeps the port pinned for the whole review,
so the tab survives restarts. You read the diff while it triages. Nothing reaches GitHub until you say
so, every round.

```bash
python3 skills/review-pr/scripts/render.py --selftest   # also checks the badges match the contract
```

## Design notes

**Nothing assumes one agent.** Skills reference their own files relative to themselves, the scripts
resolve the bundle from `$BASH_SOURCE`, and `render.py` finds the contract next to itself — so the set
works wherever it is installed. Where a skill says *load the review-exchange skill* or *ask a
multi-select question*, use whatever your agent calls that. `.claude-plugin/` exists only so Claude
Code can install this in one command; every other agent ignores it.

**No scratch files in your checkout.** No `.review/`, no findings JSON, no repro script — transient
state goes to `${XDG_STATE_HOME:-~/.local/state}/review-pr`, override with `REVIEW_STATE_DIR`. Your
branch is never checked out from under you either: `/review-pr` adds a detached worktree at
`<repo>/.claude/worktrees/review-pr-<n>` and works there. That path is inside the repo, so **add
`.claude/` to the repo's `.gitignore`** (or to `.git/info/exclude`) or it shows up as untracked.
Remove a stale one with `git worktree remove`.

**The fan-out expects subagents.** `/review-pr` shards a large diff across parallel agents and
`/revise` fans out one agent per PR. On an agent that can't spawn them, the phases still describe the
passes — you just get them serially, in one context.
