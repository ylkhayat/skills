# Linear ticket

Goal: tickets a teammate can pick up without a meeting. Small, plain, scannable.

## The template (use it verbatim, keep it short)

Load `/ai-ethics` and lead the description with its marker for non-GitHub surfaces
(`_Generated by Claude Code_`), then a blank line, then the template. A ticket I drafted is
published prose under a human's account, so it is marked like any other posting. Do not type
the marker from memory, the skill owns its exact form.

```
_Generated by Claude Code_

## Context
<1–3 lines: what triggers this, the constraint that matters, and any edge case
stated inline. Link related tickets here as plain PLT-123 refs (Linear auto-links).>

## Task
<one lead line naming the deliverable, e.g. "Implement a cron job that:">
* concrete requirement
* concrete requirement
* the edge case handled

**References**
PLT-123 — what it is and why it is linked
PLT-456 — ...
```

Context frames the situation and folds in edge cases; Task is the concrete work as
plain bullets (not checkboxes); References links dependencies and consumers, one line
each. Drop the References block if there is nothing to link. If the Task needs more
than ~6 bullets it is probably two tickets.

## Title

- Imperative and specific: "Write a usage row when a call ends", not "Usage row" or "Implement the writing of usage rows".
- No ticket-ID prefix, no "[Backend]" tags (use the team/label/project fields for that).
- One outcome per title. If it has "and", check whether it is two tickets.

## Scoping

- One ticket = one shippable, reviewable unit. A reviewer should be able to say yes or no to it alone.
- Acceptance criteria are things you can observe, not implementation steps. "Org cap blocks a new call once reached" beats "add canStart check in router".
- Put what is explicitly NOT in this ticket under Notes if it is likely to be assumed.

## Prose: humanize it

Run the prose through the /humanizer principles before saving. In short:
- No em dashes or en dashes anywhere. Use a period, comma, colon, or parentheses.
- Plain active voice. "Twilio reports the seconds" not "the seconds are reported".
- No filler or inflation: drop "robust", "seamless", "leverage", "in order to", "it is important to note".
- No rule-of-three padding, no boldface sprinkled mid-sentence, straight quotes only.
- Say the thing once. Cut any sentence that only restates the title.

## Which state does it go in

The state names below are my team's (`issue tracker` in `../review-exchange/config.md`). Another workspace
renames them; the split — committed work in the ready state, cancellable work parked — does not.

- **Committed / ready to execute** → the team's ready state (Todo, or Backlog if not this cycle). These are agreed, in-scope work.
- **Cancellable / still under refinement** → **Triage**. Anything that is a stretch goal, descopable, or blocked on an open decision goes here. Triage is the honest home for "we might not do this", so it does not read as a commitment.
- A ticket blocked on a decision links that decision in Notes and stays in Triage until the decision lands.

## Fields to set when creating

Set what you know, skip what you would have to guess:
- `team`, `project`, and `milestone` (map each ticket to the milestone it belongs to).
- `state` per the rule above.
- `estimate` only if the team uses points and you have a real number. For a t-shirt team the field is still numeric: 1=XS, 2=S, 3=M, 5=L, 8=XL. Set the number; Linear renders the size. Prefer the estimate field over effort labels when the team has estimates enabled.
- Leave assignee, labels, and priority unset unless the user gave them. Do not invent labels: list the team's labels first and use those.
- Labels in the same Linear group are mutually exclusive (e.g. a "Category" group lets you apply only one of its children). Pick one per group or the create fails.
- To mark a duplicate, set the `duplicateOf` relation first (that alone flips the issue to the Duplicate state). Setting the Duplicate state without the relation fails.
- This MCP cannot clear or delete a milestone: `save_issue` only *sets* a milestone (null/empty are ignored or rejected) and `save_milestone` has no delete. Removing milestones has to happen in the Linear UI.
- Group related tickets under a parent/epic with `parentId`. Create the parent first, then set `parentId` on each child. Leaving some issues unparented is fine.
- Moving issues to another team reassigns their identifiers (e.g. ENG-123 becomes PLT-45). Cached IDs go stale and updates 404. Re-list the project to get the new IDs before editing.
- State IDs are per-team. After a move, passing the old team's state UUID fails with a team/state discrepancy. Pass the state by name ("Canceled", "Triage") so it resolves within the issue's current team.
- Titles carry no scope tag by default. If the user asks for prefixes ("Backend:", "Frontend:", "Agent:"), add them; their ask overrides this.

## Flow

1. Draft titles and group by milestone. Confirm the execution vs. Triage split with the user if it is not obvious.
2. Write each description with the template, marker first, then humanize.
3. Create them. Report back as a short list grouped by state, with the Linear URLs.
