# The review body

One review-level comment, and at submit it becomes the GitHub review body — the one thing every reader
of the PR sees. `render.py body` assembles it from the top-level fields of `findings.json`; you write
the fields.

```markdown
[![Generated by Claude Code](…)](https://claude.com/claude-code)
![Round 2](https://img.shields.io/badge/Round-2-1f2328?style=flat-square)

**AI;DR** — <2–3 sentences, one paragraph, no bullets, no headings.>

**Reviewer note**
> Way to go!

`ENG-4406 · Follows` · 12 files · 2 open · 1 fixed · rung 4 · didn't run: migration rerun (no local DB)

| | Where | Claim |
|---|---|---|
| ● HIGH blocking | [`VoiceIdSection.tsx:203`](<thread url>) | Deletion inherits the VoiceID feature flag |
| ● MED question | [`DeleteAccountSection.tsx:39`](<thread url>) | Failed precheck leaves the button a no-op |
| ✓ LOW non-blocking | [`VoiceIdSection.tsx:15`](<thread url>) | Legacy delete block still renders |

**Takeaway** — <one or two lines, deduplicated across the threads.>
Endorsed 2 of cursor[bot]'s, not endorsed 1 (predates this PR).
```

| Field | |
|---|---|
| `round` | Line 2, under the ai-ethics marker. `pr-context.sh` computes it; the renderer draws the badge. **Review body only** — never an inline comment, never a reply. |
| `aidr` | **2–3 sentences, hard cap.** What the change does and how it sits in the system, the one load-bearing fact it is safe because of, and where the review landed. The renderer warns at 4. |
| `reviewer_note` | The reviewer's own line, **verbatim**. |
| `ticket` / `verdict` | `Follows` / `Supplements` / `Partial` / `Contradicts` / `Unrelated`. Omit `ticket` entirely when there is none. |
| `meta.files` / `meta.rung` / `meta.didnt_run` | The honest half. Counts come from the findings. |
| `takeaway` | What survives the merge — the rule a developer keeps. Drop it when every finding was a one-off. |
| `on_others` | One line on the endorsements. Drop it when there were none. |
| `gif` / `gif_word` | `APPROVE` only, appended at 200px. |

- **The AI;DR carries the verdict, so nothing else has to.** It absorbs what used to be four sections.
  A fourth sentence means a finding has escaped the ledger and belongs in a thread.
- **The metadata line is the honest half.** "No HIGH found" and "no HIGH there" are different
  sentences, and `didnt_run` is where the difference lives. **No coverage checklist** — a box ticked
  "clean" is theatre, and what you skipped fits here in eight words.
- **The ledger is the navigation hub.** The status glyph rides in the first cell with the severity and
  the ask: `●` open, `✓` fixed, `↩` answered, `—` theirs. One row per finding, most severe first,
  `Where` linking to the thread once submit has paired them, and the claim worded exactly as the
  comment's own claim so the row and the thread are recognisably the same thing. Capped at eight rows,
  then `+N more in the threads below`. Words, not badges — a column of badges turns the table into noise.
- **A scope cluster corroborates a `Supplements` verdict**, and past `scope-lens.md`'s three-cluster
  cap it *replaces* the threads: one AI;DR sentence naming the two PRs this really is, and no rows.
- **Every row is `●` on round 1.** Phase 6 edits `status` and the counts follow.
- **The reviewer note is theirs, verbatim.** One sentence in their own voice, sitting under the AI;DR
  where the author reads it first. Phase 5 asks for it; you never write it, never round a fragment out
  into prose, never supply one they didn't give. Typos and exclamation marks included — the point of it
  is that one line on the page is not yours. The renderer drops both lines when the field is empty.

## The event

`render.py event` decides, off the asks, never the severities:

| Surviving asks | Event |
|---|---|
| any open `blocking`, or any open `question` | `COMMENT` |
| only `non-blocking` | `APPROVE` |
| nothing at all | `APPROVE` |

**Never `request-changes`**, however severe the findings — severity is a badge, not a gate on the
author's branch. `gh-review.sh` refuses any other event. A round where every `blocking` was verified
fixed is exactly the approve case: approve it, and let the ledger carry the history.

Three things pull an otherwise-approvable review back to `COMMENT`. The first is automatic; set
`force_comment: true` for the other two:

- **A ticket verdict of `Contradicts`.** The diff working against what the ticket specifies is a finding of its own, whatever the badges say. The renderer applies this one itself.
- **A HIGH-risk area you could not verify.** If `didnt_run` is hiding something that would be a HIGH if it went the other way — a migration you could not run, a claim resting on a base PR that has since moved — say so and stay at `COMMENT`.
- **An open question whose answer could be a HIGH.** A `question` filed because severity was unclear is not automatically a LOW.

A stacked PR is judged on its own merits: the base still being under review is not a reason to withhold
approval, since the approval is against that base.

## Asking for the note and the GIF

Both in **one message**, before building the payload — never two round-trips, and never a blocking one:

> Ready to post. Want a reviewer note? (One line, goes at the top in your words.) Approving this one,
> so I'd caption it **ship it** — got a GIF for it? Say skip to either.

**You do not go looking for a GIF URL** — no web search, no guessing at a Giphy link that 404s into the
review body. Suggest the word, let them hand you the image. Skip, silence, or no URL means post without
it; this waits on the reviewer, it never blocks the submit. Match the word to the review rather than
reusing one: a clean approve, an approve carrying nits, and an approve after a fix you enjoyed are three
different words.
