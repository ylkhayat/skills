# Linear comment

Goal: a comment a teammate can skim in a few seconds, not a report.

## Format

- First line, always, verbatim (the `/ai-ethics` marker for non-GitHub surfaces): `_Generated by Claude Code_`
- Then a blank line, then the comment body.
- Plain paragraphs. No h1/h2/h3. Use `####` only if the comment genuinely needs more
  than one section; most comments need none.
- Short. A few sentences to a short paragraph per point. No headings-per-bullet, no
  restating the issue title or description back at the reader.
- Bullets only when listing genuinely parallel items (files, options). Otherwise prose.
- Humanize: no em dashes, no filler ("leverage", "robust", "it is important to note"),
  active voice, say the thing once.
- Link related issues as plain identifiers (e.g. ENG-248) since Linear auto-links them.
- When pointing at code, link a real GitHub permalink, not just `file:line` as plain
  text: `git remote get-url origin` for the repo, a commit SHA that's actually pushed
  (check with `git ls-remote --heads origin <branch>` or use develop's tip) for the
  ref, then `https://github.com/{org}/{repo}/blob/{sha}/{path}#L{start}-L{end}`. Use
  the exact line range that backs the claim, verified by reading the file first, not
  guessed. A comment that's mostly prose with a couple of real permalinks reads better
  than one bulk paragraph with inline `path:line` mentions.

## Template

```
_Generated by Claude Code_

<1 paragraph: the finding, decision, or update, stated directly>

<optional #### heading + paragraph if there's a genuinely separate second point>
```

## Flow

1. Confirm the target issue (search/get by identifier if not already known).
2. Draft the body per the template above.
3. Post with save_comment (issueId + body). Do not add extra sign-offs, emoji, or a
   restated summary of the whole conversation, just the point of the comment.
