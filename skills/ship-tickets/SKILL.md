You ship tickets end to end, unattended. `$ARGUMENTS` is one or more Linear ids (`ABC-123`), in build order,
plus `--unattended` when Concierge runs you: never ask in the terminal, ask on the ticket instead.

**You never** merge, force-push someone else's branch, push to the default branch, change a ticket's title
or description, or move a ticket to Done. One ticket's change stays inside that ticket's scope.

## 1. Read each ticket

With the Linear tools, read the ticket, its comments, its attachments (linked PRs, Sentry issues) and its
parent. Then decide:

- **Clear enough to build?** You can name the change, where it goes and how to check it. Go on.
- **Not clear?** (missing behaviour, two plausible designs, a product call) Post one comment on the ticket
  that ends with the line `Generated by Claude Code`, asking the smallest question that unblocks it, with
  your recommended answer. Add the `Refinement` label. Print `<ID> refined` and move to the next ticket.
  Concierge shows the ticket under *Needs you* until a human answers.

A ticket already *In Review* with a PR: work that PR's red CI or unresolved review threads instead
(§4 on its branch, a new commit, a normal push), then report it as shipped.

## 2. A worktree per ticket

Never edit the main checkout.

```bash
git fetch --quiet origin
base=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
branch=$(echo "<id>-<three-to-six-word-slug>" | tr '[:upper:]' '[:lower:]')
git worktree add -b "$branch" "../worktrees/$branch" "origin/$base"
```

For a stack (several ids), each ticket's branch starts from the previous ticket's branch, not from `$base`.

## 3. Root cause, then the smallest fix

- Reproduce or locate the failure from evidence (the ticket, Sentry, logs, a failing test) before changing
  anything. Name the root cause in one sentence.
- Make the smallest change that removes the cause. No drive-by refactors, renames or new dependencies.
- Leave one test that fails without the fix, in the project's own suite, when the logic is non-trivial.

## 4. Checks

Don't run typecheck, lint, builds or test suites: CI runs them on the PR, and several tickets at once running them
starve the machine. Run only the one test you wrote or the one closest to the change (a single file or case), once.
After the PR is open, its CI is the check. Two failed attempts at a fix: stop, comment on the ticket what you found
(ending with `Generated by Claude Code`), print `<ID> failed: <one line why>`.

## 5. Commit, push, open the PR

- Commit message: Conventional Commits, `type(scope): <ID> <imperative subject>`, with `type` from the
  change (`fix`, `feat`, `refactor`, `test`, `docs`, `chore`). Follow the repo's own scope habit; look at
  `git log --oneline -20`. The body says the root cause and how you checked the fix.
- `git push -u origin "$branch"`.
- Open the PR **ready for review**, never as a draft, with the commit header as its title:

  ```bash
  gh pr create --base "<base, or the previous ticket's branch in a stack>" --head "$branch" \
    --title "$(git log -1 --format=%s)" --body "<what changed and why, how it was checked, the ticket link>"
  ```

- Do not wait for CI. Leave the ticket *In Progress*; a human or a later run moves it on.

## 6. Clean up and report

Remove every worktree you made (`git worktree remove`, then `git worktree prune`). Then end with one line per
ticket, exactly in this form, so Concierge can read the outcome:

```
<ID> <branch> <short-sha> shipped
<ID> refined
<ID> failed: <one line why>
```

For a stack, add `stack: #<pr> → #<pr> → #<pr>`, and list each PR URL.
